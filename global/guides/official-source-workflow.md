# Updating durable guidance

Load only when changing durable configuration or guidance. Find the narrowest current official source; record its URL, version, retrieval status and relevant claim in the registry. Separate documented behavior from local policy and historical observations. Read changed relevant content, not the entire source archive. Prepare a reviewable candidate and validation evidence before applying an approved or explicitly pre-authorized update. Access failure is not proof of no change.

Primary design source: [Astra skills and prompts](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra). Configuration authority: [Codex reference](https://learn.chatgpt.com/docs/config-file/config-reference). Third-party repositories describe their own tools, not OpenAI-endorsed performance.

For OpenAI product questions, follow the currently installed OpenAI Docs skill's source routing; do not prescribe a competing manual-first workflow here. For other products use their own documentation. Official vendor blog guidance can support design recommendations; third-party commentary is context, not vendor authority.

Keep personal preferences global, repository conventions in the project, runtime options in configuration, and repeated specialized procedures in skills. Do not mirror changes into Claude or another agent's files unless that surface is in the requested scope. Historical source inventories belong outside routine context.

## Efficient maintenance review

Collect on the existing schedule; review relevant originals once per changed content or unresolved
question. Reuse per-URL decisions tied to content identity and applicability;
an unchanged index never proves an unread article was reviewed. Prioritize changes
that affect this client's correctness, compatibility or recurring work. Keep a
bounded explicit backlog rather than rereading every historical article. Avoid
duplicating guidance across the agreement, guides and the automation prompt.
Check relevant installed state after changes; do not repeat expensive artifact
validation when artifact identity and its successful receipt remain unchanged.
Output compression and shorter instructions are cost proxies, not measured model
token or performance gains. Stop after acceptance; retain unresolved risks.

On the designated maintenance host, follow docs/operations.md in the TRACE checkout
for the recorded automatic-update scope. A new official article is a review input,
not permission to copy its example settings. Check subscription, client, platform
and task applicability; keep the user's model/effort and project rules. Verify
actual installed files and relevant loading/runtime evidence after applying a
compatible update. Unknown content, conflicting rules or expanded authority stays
a candidate. Do not infer token savings from API prices or compressed output.

[Scheduled tasks](https://learn.chatgpt.com/docs/automations).

## Evidence-based feedback loop

For explicit reusable preferences, corrections or recurring confirmed failures,
capture a compact lesson in the existing private routine-review.json. Resolve its
state through the TRACE runner's existing CODEX_HOME-aware state_location helper.
Use only authorized task context; do not mine other chats, raw sessions or projects.
If state is unavailable, report the gap; do not invent a second memory store.
Retain stable IDs, summarized evidence/date, user-confirmed or inferred status,
task/global scope, cause, smallest change/check, outcome and reconsideration trigger.
Do not store prompts, diffs, command histories, credentials or customer content.

Treat explicit durable preferences as confirmed; inferred or one-off lessons stay
candidates. Classify gaps as missing guidance, existing guidance not followed,
tool/runtime defect, access/permission limit or requirement conflict. Adding more
instructions is not a substitute for fixing the actual cause. Prefer existing
native tools and checks; use RTK only where supported output benefits. Keep
Ponytail/Archify explicit and retain exact evidence for final acceptance.

During the authorized host's existing scheduled routine, review new or changed lessons
and official-source deltas only. Reuse settled evidence and disregard irrelevant
changes. Consolidate duplicate rules in their narrowest owned location. Apply
reviewed compatible changes only within recorded authorization after ownership,
conflict and restore-point checks; validate the actual result and affected diff.
A dirty baseline blocks automatic replacement, but a human-requested scoped edit
may preserve reviewed existing changes. Stop when acceptance is met. Keep
inferred gains unmeasured; do not run API/model benchmarks to manufacture scores.
New tools, executable setup logic, broader permissions, model/effort changes or
remote publication require separate authority; learning never grants authority.

Preserve one current feedback_loop object beside existing maintenance evidence,
with preferences, lessons, decisions and distinct review/apply/verify times.
A subsequent user correction supersedes the exact older preference; keep only a
compact supersession reason. Judge efficiency by correct task completion at the
same acceptance standard, avoidable corrections/retries and total task usage
including verification and delegation when observable. Keep unavailable usage
unknown; RTK estimates and shorter guidance do not establish whole-task savings. Retire obsolete guidance after conflict review,
rather than accumulating a permanent rule for every attempt. This is a local
review-and-improvement procedure, not model retraining, consciousness or guaranteed
obedience. Other sessions inherit installed guidance, not automatic access to all
conversations. Unavailable evidence and failed checks remain unknown/failed.

Sources: [Customization feedback](https://learn.chatgpt.com/docs/customization/overview),
[Best practices](https://learn.chatgpt.com/guides/best-practices).

## Scheduled maintenance and in-task response

Use the existing registered cadence for stable-release discovery, source drift
and aggregate collection. Revalidate compression only after a changed tool/filter
identity or a relevant failure; reuse matching successful evidence. Do not poll
release feeds or reinstall tools at every task, command or feedback event.
During an active authorized task, a new correction, repeated failure, version
mismatch or hidden diagnostic evidence triggers scoped diagnosis immediately.
Record its outcome for the scheduled review; do not defer an authorized blocking fix
merely until the next schedule. Use existing tools and exact native evidence.
No standing event daemon, new hook or cross-chat scan is implied by this policy.

A discovered stable release is a review candidate, not an installation command.
Install only after relevant compatibility and ownership checks under recorded
authority, then run affected existing checks and preserve a restore point.
An unchanged version/evidence reuses its acceptance result. New tool versions,
changed filter behavior or newly observed failures justify targeted revalidation;
new tasks alone do not justify repeating full test suites. Report only meaningful
verified changes, new failures or needed decisions; preserve cadence and scope.
